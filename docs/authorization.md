# Authorization — Phase 6

`lib/authorization/server.ts` is the server-only entry point. `requirePrincipal()` validates the current session, account status, and email verification, then reloads database roles. `requireRole()` checks explicit membership; administrators do not inherit unrelated roles. Customer access requires a customer profile; technician access also requires an active, verified technician profile. Membership is never accepted from browser data or cached in session claims.

Protected `/portal/customer`, `/portal/technician`, and `/portal/admin` pages enforce these checks before rendering. `/account` shows only permitted workspace links. These are access-controlled starting pages, not completed dashboards. Anonymous visitors go to login; unauthorized or unknown workspaces render the generic not-found page. Next streaming may carry redirects/not-found content in a 200 response; denial tests verify no protected heading is rendered.

`requireJob(id)` resolves identity from the session and returns only an authorized job summary. Its testable database policy, `readAuthorizedJob`, allows administrators, the owning customer, or the active verified technician on a current pending/accepted assignment. Ending an assignment removes technician access. Invalid, missing, and inaccessible IDs return the same absence result. The explicit projection excludes location/contact details, internal notes, and other relations. Low-level policy functions take trusted server identities only; public handlers must use the session-bound wrapper.

These are read permissions. Future mutations must check action-specific permissions, workflow state, and current assignment within their transaction. Future APIs must enforce authorization themselves and use appropriate 401/403/404 responses; hiding navigation or protecting a layout is insufficient. Category/area eligibility is a future assignment-creation rule. Role grants, technician verification, and audit trails require the later administrator workflow; no public elevation endpoint or production administrator bootstrap is supplied here.

Verification: `npm run test:authorization` runs four transactional PostgreSQL tests for ownership, role isolation, technician eligibility/current assignment, immediate revocation, multi-role accounts, and safe projections. `npm run test:auth:http` now also attempts direct role URLs, grants/revokes test-only memberships, and changes technician eligibility while reusing the same real session. Fixtures use only the guarded test database and are rolled back or removed. Lint/type checks and a production build remain required. Browser interaction and SMTP delivery checks remain outstanding from earlier phases.

No migration or dependency was added. The PostgreSQL adapter emitted a pg 8 deprecation warning about concurrent queries during one integration run; tests passed. Recheck adapter compatibility before upgrading to pg 9.
